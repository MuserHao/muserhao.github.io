Landing the Actor-Critic: DQN, A2C & PPO in the Browser

// ~4,200 parameters, zero GPUs, and the visualization that makes RLHF click

01 // THE SETUP

After building RL Pong with Q-Learning, DQN, and REINFORCE, the natural next step was the algorithm family that actually runs the modern world: Actor-Critic methods. A2C is how DeepMind's agents learn. PPO is how ChatGPT was aligned via RLHF. And if you read When GANs Meet RL, you already know the punchline — the actor is the generator, the critic is the discriminator. Same adversarial game, different costume.

Lunar Lander was the obvious vehicle. It fits the space theme, has intuitive physics anyone can understand (gravity goes down, thrust goes up), and the 6-action space is rich enough to show real behavioral differences between algorithms. Most importantly, the actor-critic split is visually demonstrable: you can watch the critic’s confidence rise as the lander approaches the pad, and the actor concentrate probability mass onto main-thrust.

The goal: implement DQN (baseline visitors know from Pong), A2C (the core teaching algorithm), and PPO (the modern standard) — all training live in the browser with a real-time actor-critic visualization panel.

02 // THE THREE ALGORITHMS

DQN — The Baseline

DQN is the same Double DQN from Pong, scaled up to 6 actions. One network estimates $Q(s, a)$ for all actions; the agent picks $\arg\max_a Q(s, a)$ (with $\epsilon$-greedy exploration). The target network stabilizes learning:

$$Q(s, a) \leftarrow r + \gamma \, Q_{\text{target}}(s', \arg\max_{a'} Q_{\text{online}}(s', a'))$$

Architecture: MiniNet2(8, 64, 48, 6) = ~2,200 parameters. It works, but it only learns values — there’s no explicit policy. This is where actor-critic enters.

A2C — Advantage Actor-Critic

A2C splits the brain in two. The Actor $\pi_\theta(a|s)$ is a policy network that outputs a probability distribution over actions. The Critic $V_\phi(s)$ is a value network that estimates how good the current state is. The key insight: instead of using raw returns as in REINFORCE, we use the advantage:

$$A(s, a) = r + \gamma \, V_\phi(s') - V_\phi(s)$$

This is the TD (temporal difference) advantage — “how much better was this outcome than what the critic expected?” A positive advantage means “do more of this,” negative means “do less.” The actor’s policy gradient becomes:

$$\nabla_\theta J \approx \nabla_\theta \log \pi_\theta(a|s) \cdot A(s, a)$$

And the critic trains via MSE on the TD target:

$$\mathcal{L}_{\text{critic}} = \Big( r + \gamma \, V_\phi(s') - V_\phi(s) \Big)^2$$

Two networks, two loss functions, one elegant loop. Actor: MiniNet2(8, 64, 48, 6) = ~2,200 params. Critic: MiniNet2(8, 64, 48, 1) = ~2,000 params. Total: ~4,200 parameters.

PPO — Proximal Policy Optimization

PPO is A2C with guardrails. The problem with vanilla policy gradients: a single bad update can destroy a good policy. PPO’s fix is the clipped surrogate objective:

$$L^{\text{PPO}} = \mathbb{E} \Big[ \min\!\big( r_t(\theta) \, A_t, \; \text{clip}(r_t(\theta), 1-\epsilon, 1+\epsilon) \, A_t \big) \Big]$$

where the importance ratio $r_t(\theta) = \pi_\theta(a_t|s_t) / \pi_{\theta_{\text{old}}}(a_t|s_t)$ measures how much the policy has changed. If the ratio drifts too far from 1 (policy changed too much), the clipping kicks in and stops the gradient. This is why PPO is the algorithm of choice for RLHF — it makes large policy changes safely.

PPO also uses Generalized Advantage Estimation (GAE) instead of single-step TD:

$$\hat{A}_t = \sum_{l=0}^{T-t} (\gamma \lambda)^l \, \delta_{t+l}, \quad \delta_t = r_t + \gamma V(s_{t+1}) - V(s_t)$$

The $\lambda$ parameter (0.95 here) interpolates between high-bias/low-variance (TD, $\lambda=0$) and low-bias/high-variance (Monte Carlo, $\lambda=1$). Same architecture as A2C: ~4,200 parameters.

03 // THE PHYSICS

Everything runs in an 800×600 logical coordinate space (same as Pong). The physics are deliberately simple — just enough to make landing non-trivial:

  • Gravity: 0.04 px/frame² downward (gentle moon gravity)
  • Main thrust: 0.15 px/frame² along the lander’s up axis
  • Side thrusters: 0.05 px/frame² for lateral translation
  • Rotation: ±0.04 rad/frame, with angular damping of 0.98
  • Wind gusts: random, max 0.02 px/frame² (enabled at curriculum level 3)

These values went through iteration. We originally used gravity 0.05 and thrust 0.12, giving a thrust-to-gravity ratio of 2.4×. The agent needed to fire thrust 42% of the time just to hover — too demanding for a random exploration policy that only picks each of 6 actions ~17% of the time. Bumping to gravity 0.04 and thrust 0.15 (ratio 3.75×) means hovering requires thrust only 27% of the time, giving the agent enough control authority to accidentally discover braking.

Terrain is generated via midpoint displacement — a fractal algorithm that produces realistic mountainous profiles. An 80px-wide landing pad is placed randomly in the middle third of the terrain, painted neon green with glow.

The lander itself is a triangle with two legs, rendered in neon cyan with animated thrust flames (particle system). Landing criteria: both leg tips on pad, $|\theta| < 20°$, $|v_y| < 1.5$, $|v_x| < 0.8$. We relaxed these from the initial values ($15°$, $1.0$, $0.5$) after discovering that the 4-pixel landing window was too tight for small networks to hit reliably. 

// 6 discrete actions
const ACTIONS = {
    NOOP: 0,
    THRUST_MAIN: 1,
    THRUST_LEFT: 2,
    THRUST_RIGHT: 3,
    ROTATE_LEFT: 4,
    ROTATE_RIGHT: 5
};

04 // THE REWARD THAT BROKE EVERYTHING (TWICE)

The state is an 8-dimensional vector, all normalized to roughly [-1, 1]: 

const state = [
    (lander.x - padCx) / W,      // pad-relative X
    (lander.y - padCy) / H,      // pad-relative Y
    lander.vx / 5,                // normalized horizontal velocity
    lander.vy / 5,                // normalized vertical velocity
    lander.angle / Math.PI,       // normalized angle
    lander.angVel / 0.2,          // normalized angular velocity
    leftLegContact,               // binary: left leg on pad
    rightLegContact               // binary: right leg on pad
];

The reward function went through four iterations. This is the part the textbooks leave out.

Iteration 1: The obvious approach (0% landing)

We started with what every RL tutorial suggests: a simple distance-based shaping reward with big terminal bonuses. 

// v1: textbook approach
reward = -distance_to_pad * 0.5;     // per frame: ~-0.5
reward -= Math.abs(angle) * 0.3;     // angle penalty
if (landed) reward = +100;           // terminal: +100
if (crashed) reward = -100;          // terminal: -100

Result: 0% landing after 200 episodes. The agents approached the pad (min distance ~0.02) but crashed every time. Why? The distance reward increases as the lander falls — gravity does the work for free. The agent gets rewarded for doing nothing. By the time it’s near the pad, it’s going too fast to land, and the speed penalty only activates in the last 90 pixels. Too little, too late.

Lesson: reward shaping that correlates with natural dynamics is useless. If gravity already makes you closer to the pad, rewarding closeness teaches nothing.

Iteration 2: The dynamic range problem (14% DQN, 2% A2C/PPO)

We redesigned the reward to use a closeness × slowness product — you only get rewarded for being close AND slow simultaneously. This teaches braking. But we kept the terminal rewards at ±100. 

// v2: closeness × slowness
reward = closeness * max(0, 3 - speed) * 0.5;  // per frame: ~+3
if (landed) reward = +140;                       // 46x larger!
if (crashed) reward = -100;                      // 33x larger!

Result: DQN hit 14%, but A2C and PPO were stuck at 2%. The problem: a 240× dynamic range between per-frame rewards (~1) and terminal rewards (~140). A tiny neural network trying to predict $V(s)$ with MSE loss sees gradients that vary by two orders of magnitude. The critic can’t converge, so the advantages are noise, and the actor learns nothing.

DQN survived because its replay buffer averages over many transitions, dampening the spikes. A2C and PPO, which train on recent experience directly, were destroyed.

Lesson: reward scale matters as much as reward shape. If your terminal reward is 100× your step reward, the critic will spend all its capacity modeling the terminal transition and learn nothing about the approach.

Iteration 3: Normalized rewards (13% DQN, 53% A2C, 2% PPO)

The fix was simple: scale terminal rewards to ±10 instead of ±100, keeping them only ~3–5× the per-frame rewards. We also added a graduated crash penalty (soft crashes near the pad are less punishing) and an altitude penalty (discourages flying away). 

// v3: normalized scale
reward = closeness * max(0, 3 - speed) * 0.3;  // per frame: ~+2
if (landed) reward = +10 + bonuses;              // terminal: ~+14
if (crashed) reward = -2 - 3*speed - 5*dist;    // terminal: ~-5 to -10

A2C went from 2% to 53% in one change. The critic could finally predict $V(s)$ accurately because the target values were in a consistent range. The advantages became meaningful, and the actor got clear gradient signal.

Lesson: this is arguably the single most important practical lesson in RL engineering. If your rewards span orders of magnitude, normalize them. The theory says the optimal policy is scale-invariant; the practice says your ~4,200-parameter network is not.

Iteration 4: Two hidden layers (6% DQN, 5% A2C, 4% PPO)

That 53% A2C was a lucky run. Averaging over 3 trials: DQN 2%, A2C 9%, PPO 0.5%. Stochastic initialization matters enormously with tiny networks.

The deeper problem: a single ReLU hidden layer can only represent piecewise linear functions. But the value function for Lunar Lander is non-linear — it depends on interactions between position and velocity (close + slow = good, close + fast = bad). A single layer can’t capture $\text{closeness} \times \text{slowness}$ without dedicated features.

We added a second hidden layer: MiniNet2(8, 48, 32, 6). The extra layer lets the network compute intermediate features in the first layer (closeness, speed, uprightness) and combine them non-linearly in the second. The parameter count roughly doubles, but the representational capacity increases far more.

Averaged over 3 trials at 500 episodes: DQN 6%, A2C 5%, PPO 4%. Not headline numbers, but consistent and improving. More importantly, PPO went from 0.5% to 4% — the extra capacity let the clipped updates accumulate meaningful policy changes instead of getting stuck.

Lesson: at this scale, you hit the representation bottleneck before the data bottleneck. A 1,000-parameter single-layer network can’t represent the value function accurately enough for gradient-based learning to work. Two layers with the same total parameters performs dramatically better because function composition is more expressive than function width.

Iteration 5: Biased exploration + reward scaling (30% DQN, 18% A2C, 22% PPO)

Two final insights pushed the numbers up dramatically.

Biased exploration. When the agent explores randomly ($\epsilon$-greedy), it picks uniformly from 6 actions. THRUST_MAIN fires 17% of the time. But hovering requires thrust 27% of the time (gravity 0.04 / thrust 0.15). Random exploration is biased against the correct behavior. The agent spends hundreds of episodes failing before it accidentally discovers that firing thrust is essential.

Fix: weight THRUST_MAIN at 40% of random actions. This is not cheating — it’s an informed prior. We know the lander needs thrust to fight gravity; we’re just telling the exploration policy. The learned policy discovers the optimal thrust timing on its own. 

// Biased random action — THRUST_MAIN gets 40%, others 12% each
function biasedRandomAction() {
    var r = Math.random();
    if (r < 0.40) return 1; // THRUST_MAIN
    var others = [0, 2, 3, 4, 5];
    return others[Math.floor((r - 0.40) / 0.12)];
}

Reward scaling for on-policy methods. Even with normalized rewards (terminal ±20, per-frame ±3), the 7× ratio still caused critic oscillation in A2C and PPO. DQN was fine because the replay buffer averages over thousands of transitions. Fix: multiply rewards by 0.1 before passing to A2C/PPO critics. DQN keeps raw rewards.

Combined effect, averaged over 3 trials at 1,000 episodes:

  • DQN: 30% (range 8–52%) — replay buffer + biased exploration
  • A2C: 18% (range 16–21%) — finally consistent
  • PPO: 22% (range 21–23%) — the most consistent algorithm

PPO went from 1% to 22% and became the most reliable learner, with only 2% variance across trials. This is exactly what the theory predicts: PPO’s clipping prevents catastrophic updates, so once it finds a decent policy, it never loses it. A2C is faster to find good policies but can lose them to a bad gradient step. DQN has the highest ceiling (52%) but the widest variance (8–52%) depending on replay buffer composition.

For reference, OpenAI Gym’s Lunar Lander benchmark uses 2-layer networks with 64 neurons each (~8,000 parameters) and trains for 1,000+ episodes with a GPU. We’re doing it in the browser with ~4,200 parameters and pure JavaScript backprop. The agents land 20–30% of the time on easy difficulty — not human-level, but visibly improving, which is the teaching point.

What didn’t work (the graveyard)

Not every idea improved things. Here’s what we tried and reverted, and why:

  • Aggressive DQN training (batch 64, LR 0.003, train every 2 steps): made DQN worse (13%→8%). With 4K parameters, each gradient step moves weights a lot. More frequent training with bigger batches = Q-value oscillation. The replay buffer already provides diversity; training harder on it just overfits to recent transitions.
  • Frame skipping (decide every 4 physics frames, like Atari DQN): helped A2C (+7pp) but destroyed DQN (−19pp) and PPO (−17pp). At Atari scale (10,000+ frames/episode), frame skip reduces redundancy. At our scale (35 frames/episode), every frame already has meaningful state change. Frame skip just reduces training data volume, which kills replay-based and trajectory-based methods.
  • PPO per-episode trajectory flushing: theoretically correct (prevents cross-episode contamination in GAE). Practically catastrophic — training on 30-step fragments with 2 epochs is 60 gradient updates on tiny data. The agent learned to crash faster (avg steps 45→27). Reverted to accumulating across episodes with done-flag handling.
  • Landing reward +30: helped DQN (replay buffer absorbs spikes) but killed A2C/PPO. The dynamic range problem returned through the critic — same bug, different door.
  • Step-function near-pad bonus (jumps from 0 to +3 when closeness > 0.7 and speed < 2.0): neural networks hate discontinuities. Replaced with smooth $\text{closeness}^2 \times (3 - \text{speed})/3$ for stable gradients at all points.
  • PPO epoch tuning (3→4→3→2): going back and forth because it was never the real bottleneck. Like adjusting the radio while the antenna is broken.

The meta-lesson: we spent most of our debugging time tuning knobs (learning rates, batch sizes, epoch counts, trajectory lengths) when the real problems were structural (exploration bias, reward scale, network depth, spawn difficulty). Knob-turning gives the illusion of progress because every run has high variance — a lucky seed can make any configuration look good. The 53% A2C result that excited us early on was just a lucky random initialization; averaged over 3 trials it was 9%.

The changes that actually mattered were all qualitative, not quantitative: biased exploration (matching the prior to the problem), reward normalization (matching the scale to the architecture), spawn altitude (matching the task to the agent’s current ability), and network depth (matching the capacity to the function complexity). If your RL agent isn’t learning, resist the urge to tune — look for a structural mismatch.

05 // THE TRAINING LOOP THAT TOOK THREE TRIES

Lunar Lander is single-player, so there’s no opponent to calibrate against. Instead, difficulty comes from curriculum learning via spawn randomization:

  • Level 0 (Easy): 35–60px directly above pad, zero velocity, zero angle
  • Level 1 (Medium): 100–180px altitude, ±40px offset, small initial velocity
  • Level 2 (Hard): 160–300px altitude, ±100px offset, initial velocity up to 1.0
  • Level 3 (Full): 200–400px altitude, ±150px offset, wind gusts

Level 0 was originally at 120–200px altitude. No agent could land — the fall was too long, the agent built too much speed, and by the time it reached the pad the crash was inevitable. Dropping level 0 to 35–60px gave agents their first landing experiences within 50 episodes, providing the positive reward signal they needed to bootstrap learning.

The level advances automatically when the rolling landing rate (last 20 episodes) exceeds 60%. Auto-train runs 200 physics steps per animation frame.

The warmup that destroyed A2C

First-time visitors see a boot animation while agents pre-train. We used “aggressive hyperparameters” to speed convergence: $\epsilon$ decay of 0.97 per episode (much faster than normal). Sounds reasonable.

For A2C, this was catastrophic. With decay 0.97, exploration collapsed from 50% to 1% by episode 50. The agent locked into whatever bad policy it had discovered during random exploration — usually “always fire main thrust” — and trained for 50 more episodes reinforcing that bad policy. Policy gradient methods need sustained exploration because they learn from the distribution they sample. Kill the exploration, kill the learning.

DQN was unaffected because its $\epsilon$ decays per step, not per episode, and its replay buffer retains diverse experiences regardless of the current $\epsilon$. This is a fundamental advantage of off-policy methods.

Fix: gentler warmup decay (0.995 per episode), and higher learning rates instead of lower $\epsilon$ to speed convergence without sacrificing exploration.

The epsilon that barely decayed

DQN’s per-step $\epsilon$ decay was initially set to 0.99995. After 150 warmup episodes (~12,000 steps): $\epsilon = 1.0 \times 0.99995^{12000} \approx 0.55$. The agent was still picking random actions half the time. We changed this to 0.9997, which reaches $\epsilon \approx 0.05$ in ~10,000 steps.

Lesson: always compute what your hyperparameters actually produce. $0.99995^{12000} = 0.55$ is not an edge case — it’s the default behavior that you’d ship to users.

06 // WHAT EACH ALGORITHM ACTUALLY DID

DQN: The Replay Buffer Saves Everything

DQN was the most consistent performer across all our reward-function iterations: 14% with bad rewards, 13% with good rewards. It never hit 0%. Why?

The replay buffer. DQN stores every transition it sees and trains on random mini-batches. This means: (1) gradient spikes from terminal rewards get diluted by hundreds of per-frame transitions, (2) the agent sees a diverse mix of experiences regardless of its current policy, and (3) rare events like near-landings get replayed many times.

DQN’s weakness: it occasionally learned to fly away from the pad. With the original reward function, there was no penalty for drifting upward, so Q-values for “hover indefinitely” and “approach the pad” were similar. Adding an altitude penalty ($-0.3 \times \text{excess\_height}$) fixed this: 58 out-of-bounds episodes dropped to 0.

A2C: The Critic Needs Calm

A2C was the most sensitive to reward design. It went from 0% to 2% to 53% across our three iterations, purely based on reward normalization. The reason is architectural.

A2C trains in N-step batches (16 steps). The critic sees recent transitions and must predict $V(s)$ from them. If the reward scale is unstable — per-frame rewards of 1 followed by a terminal reward of 140 — the critic’s MSE loss oscillates wildly. The advantages $(R - V)$ become noise. The actor gets random gradient updates. Nothing converges.

Once we normalized rewards to a 14× range instead of 240×, the critic could actually learn the value function. A2C became the fastest learner — its N-step returns give it multi-frame context that single-step TD (our first A2C attempt) couldn’t provide, while being less noisy than full-episode Monte Carlo.

The entropy bonus ($\beta = 0.04$) is critical. Without it, A2C collapses to a deterministic policy within 20 episodes. With the closeness×slowness reward, “always fire main thrust” is locally optimal — it keeps you slow — but it can’t handle lateral corrections. The entropy bonus keeps the policy stochastic enough to discover that NOOP and rotation matter too.

PPO: Conservative to a Fault

PPO’s story is the opposite of A2C’s. Where A2C was too sensitive, PPO was too conservative. Its landing rate stayed at 2% even after A2C hit 53%.

The issue: PPO needs enough data per training step to make the clipping meaningful. It collects 64-step trajectories before training. With episodes averaging 30–40 steps, each trajectory spans ~2 episodes. This is fine — GAE handles episode boundaries via done flags. But it means PPO trains half as often as A2C per episode. The clipping then further limits how much the policy can change per update.

We made PPO’s training frequency worse by accident: our first version flushed the trajectory on every episode end, training on tiny 30-step fragments with 3 epochs. That’s 90 gradient updates on 30 data points — severe overfitting. The policy degraded: average episode length dropped from 45 to 27 steps over 500 episodes. The agent was learning to crash faster.

Fix: let PPO accumulate across episodes (done flags handle boundaries), only train at 64 steps, reduce to 2 epochs. PPO is still the slowest learner but no longer degrades. With more training time (500+ episodes), it should show the smoothest learning curve.

Lesson: PPO’s conservatism is both its strength and its weakness. It needs more data per update than A2C. In production RLHF, this is solved with large batch sizes (thousands of trajectories). In a browser with ~4,200 parameters, you just need patience.

07 // SEEING ACTOR-CRITIC

This is the teaching payoff. When you select A2C or PPO, a visualization panel appears below the game canvas with two components:

The Critic Confidence Meter: a vertical bar that shows $V(s)$ in real time. It goes from red (low value — “we’re going to crash”) through yellow to green (high value — “we’re about to land”). Watch it during a trained agent’s descent: it starts low, rises as the lander aligns with the pad, and spikes green right before touchdown.

The Actor Action Probabilities: a 6-bar chart showing $\pi(a|s)$ for each action. During early training, all bars are roughly equal (random policy). As the agent learns, you see probability mass concentrate: main-thrust dominates during descent, rotation adjusts for wind, NOOP appears during stable glides. The top-probability action glows green.

If you’ve read the GAN-RL blog post, this should feel viscerally familiar. The actor is the generator — it produces actions (samples). The critic is the discriminator — it evaluates states (scores). The actor tries to take actions that the critic approves of. The critic tries to accurately predict outcomes. Same adversarial game, same convergent dynamic.

In RLHF for LLMs, the actor is the language model (generating tokens), and the critic is the reward model (scoring responses). PPO is the training algorithm. Every piece of this visualization maps directly onto how ChatGPT was trained.

08 // TECHNICAL DETAILS

trainPPO() — The New MiniNet Method

The PPO clipped objective requires a new training method on MiniNet. The key difference from trainPG(): we need the old policy’s probabilities to compute the importance ratio. 

// Importance ratio for the taken action
const ratio = newP / oldP;

// Clipped surrogate
const clipped = Math.max(1 - clipEps, Math.min(1 + clipEps, ratio));
const surr1 = ratio * advantage;
const surr2 = clipped * advantage;

// Gradient flows through the binding term
const useClipped = (surr1 > surr2) ? 1 : 0;

When the advantage is positive (action was good), the ratio is clipped from above at $1 + \epsilon$ — the policy can’t increase the probability of this action too much. When the advantage is negative, it’s clipped from below at $1 - \epsilon$. This creates a “trust region” around the old policy.

GAE Implementation

GAE computes advantages in a single backward pass over the trajectory: 

let gae = 0;
for (let t = T - 1; t >= 0; t--) {
    const delta = reward[t] + gamma * V(s[t+1]) - V(s[t]);
    gae = delta + gamma * lambda * gae;
    advantages[t] = gae;
    returns[t] = gae + values[t];
}

Each advantage is a weighted sum of all future TD errors, with exponential decay controlled by $\gamma \lambda$. At $\lambda = 0$ you get single-step TD (high bias, low variance). At $\lambda = 1$ you get Monte Carlo returns (low bias, high variance). The sweet spot at 0.95 gives smooth advantage estimates that help PPO learn stably.

Parameter Counts

Every parameter is a Float64 in typed arrays — no framework, no tensors, just arithmetic. We use 2-hidden-layer networks (MiniNet2) for the capacity to represent non-linear value functions:

  • DQN: MiniNet2(8, 48, 32, 6) → (8×48+48) + (48×32+32) + (32×6+6) = 432+1568+198 = 2,198
  • A2C/PPO Actor: MiniNet2(8, 48, 32, 6) → 2,198
  • A2C/PPO Critic: MiniNet2(8, 48, 32, 1) → (8×48+48) + (48×32+32) + (32×1+1) = 432+1568+33 = 2,033
  • A2C/PPO Total: 2,198 + 2,033 = 4,231
