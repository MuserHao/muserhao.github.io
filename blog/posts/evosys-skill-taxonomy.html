EvoSys: Teaching Machines to Build Their Own Muscles

// a taxonomy of skills, from regex to reasoning -- and how a system learns which muscle to grow

01 // THE COST OF REPETITION

Every time you ask a cloud LLM to extract a date from a string, you pay the same price. Every time it parses a JSON response, reformats a table, or classifies an email -- the same tokens flow through the same billions of parameters, burning the same compute. The task might take a human three seconds with a regex, but the LLM treats it as if it has never seen the problem before. Because it hasn't. Stateless by design, every call starts from zero.

Biology does not work this way. When you first learn to catch a ball, the entire cortex lights up -- visual processing, spatial reasoning, motor planning, error correction. It is expensive, slow, and error-prone. But repetition changes the wiring. Neural pathways myelinate. Reflexes form. Eventually the catch is handled by the cerebellum -- fast, cheap, unconscious. The expensive general intelligence that learned the skill is freed up for new problems.

This is the core principle behind EvoSys: observe, distill, specialize. The system watches itself work. It notices when the same kinds of tasks recur. And then it asks a dangerous question: can this be done cheaper?

The goal is not to replace the cloud LLM. The goal is to transform expensive general intelligence into a growing network of cheap, specialized micro-skills -- each one a frozen solution to a problem that was once costly to solve but is now nearly free to repeat. The cloud LLM becomes the teacher, not the worker. The system grows muscles.

02 // WHAT IS A SKILL?

At its most abstract, a skill is anything that accepts structured input and produces structured output. A function. A transformation. A mapping from question to answer, from raw data to processed result.

But skills span a massive spectrum. On one end: a three-line regex that extracts phone numbers from text. Deterministic. Instant. Free. On the other end: a full agent delegation that hands an ambiguous research question to Claude Code, which spawns sub-tasks, reads documentation, writes code, tests it, and returns a synthesized answer. Non-deterministic. Slow. Expensive.

Both are skills. Both accept input and produce output. But they differ by orders of magnitude in latency, cost, reliability, and the kind of intelligence they require. The regex encodes a pattern. The agent delegation encodes a reasoning process.

The question EvoSys asks is not "can we automate this?" -- almost anything can be automated at Tier 5 by throwing it at a powerful LLM. The real question is: at what level of abstraction? Can this task, which currently requires general reasoning, be reduced to something simpler? And if so, how far down can it go?

"A skill is a frozen moment of intelligence -- a solution that was expensive to discover but cheap to repeat."

03 // THE SIX TIERS

EvoSys organizes skills into six tiers, ordered by decreasing intelligence and increasing efficiency. Each tier represents a different trade-off between the generality of the solution and the cost of executing it.

Tier Name Example Latency Cost/Call Learning Cost
0Deterministic CodeRegex date extraction<1ms$0Low
1Algorithmic CodespaCy NER pipeline1-100ms$0Medium
2Cached PromptFew-shot on local 3B model100-500ms~$0Low
3Fine-tuned ModelLoRA on 0.5B model50-200ms~$0High
4Cloud LLM CallSingle Sonnet API call500-5000ms$0.001-0.01None
5Agent DelegationHand off to Claude Code5-60s+$0.05-1+None

Notice the inverse relationship: tiers 4 and 5 require no learning cost because they leverage general intelligence directly, but they pay a steep per-call price. Tiers 0 and 1 are essentially free to run, but someone -- or something -- had to invest the effort to build them. The purpose of EvoSys is to automate that investment.

THE LOWEST VIABLE TIER

Not every skill descends to Tier 0. Some tasks are inherently semantic -- they require understanding context, resolving ambiguity, or exercising judgment that cannot be captured in deterministic rules. The goal is the lowest viable tier, not the lowest possible tier. A skill that stabilizes at Tier 2 (cached prompt on a local model) is still a massive win over Tier 4 (cloud API call) -- it's faster, cheaper, and runs offline.

04 // THE DISTILLATION LADDER

Skills don't jump from cloud LLM to local regex in a single leap. The gap between Tier 5 and Tier 0 is too vast -- it spans the distance from general reasoning to pattern matching. Instead, skills descend gradually, one rung at a time, through a process we call the distillation ladder. 

Tier 5: Agent handles entire sub-task
  |  system observes, records I/O pairs
  v
Tier 4: Single LLM call with learned prompt template
  |  accumulate examples, validate consistency
  v
Tier 3: Fine-tuned local model on collected pairs
  |  analyze for deterministic patterns
  v
Tier 1: Algorithmic code (Python + libraries)
  |  simplify if rules are extractable
  v
Tier 0: Pure deterministic function

Each descent is a bet: can this be done cheaper? The system tries the next tier down, validates the output against the ground truth from the tier above, and either commits the descent or retreats. A failed descent is not a failure -- it's information. The system now knows the task's floor.

The key insight is that the intermediate tiers exist because the jump from Tier 4 to Tier 0 is too large to make reliably. Consider a task like "extract the main topic from an email subject line." A cloud LLM handles it easily at Tier 4. Can you write a regex? Almost certainly not -- subject lines are too varied. But can you fine-tune a tiny model on 500 labeled examples? Probably yes. Can you build a few-shot prompt for a local 3B model? Even easier. Cached prompts at Tier 2 are the stepping stone that makes distillation practical.

You might notice Tier 2 is missing from the ladder diagram. That's intentional -- Tier 2 (cached prompts) often serves as the first landing point for skills descending from Tier 4, before enough data accumulates to attempt Tier 3 fine-tuning. The path through the ladder is not always linear. Some skills skip tiers; others oscillate before settling.

05 // MATURATION -- FROM OBSERVATION TO MUSCLE MEMORY

Every skill in EvoSys passes through a lifecycle of maturation stages. These stages govern how much trust the system places in the skill and how much supervision it receives. 

OBSERVED ---> PROMPTED ---> SYNTHESIZED ---> OPTIMIZED ---> STABLE
                                                                       |
                                                                    DEGRADED
                                                                       |
                                                                 re-enter pipeline

OBSERVED. A recurring pattern has been detected in the system's operation logs. The same kind of input-output mapping appears repeatedly. Data is accumulating passively -- I/O pairs are being recorded, but no skill has been created yet. The system is watching and waiting for statistical confidence.

PROMPTED. Enough examples exist to construct a cached prompt. A few-shot template is created and deployed in shadow mode -- running alongside the cloud LLM on a sample of real traffic. The cloud LLM's output remains the system of record; the prompted skill's output is compared but not served. Agreement builds confidence. Divergence signals that the prompt needs refinement or the task is harder than expected.

SYNTHESIZED. The skill has been implemented as code or a fine-tuned model, with a full test suite generated from the accumulated I/O pairs. It runs in production with spot-check validation -- the cloud LLM is called on a declining percentage of requests to verify correctness.

OPTIMIZED / STABLE. The skill has proven itself over time. Shadow frequency has dropped to near zero. The skill handles its task class autonomously, with minimal monitoring. It has become muscle memory.

DEGRADED. Drift has been detected. The skill's outputs have begun diverging from what the cloud LLM would produce, or error rates have crept up, or the distribution of inputs has shifted. The skill re-enters the pipeline: shadow mode goes back to 100%, fresh examples are collected, and the Forge attempts a new synthesis.

Shadow mode deserves special attention. It is the mechanism by which EvoSys builds trust in a skill without risking production quality. Every skill, at every maturation stage below STABLE, runs alongside the cloud LLM at some sampling rate. This rate starts at 100% (every request is double-processed) and decays as agreement accumulates. The shadow comparison serves three purposes: it validates the skill's correctness, it generates training data for future improvements, and it detects degradation early.

THE TUITION FEE

Shadow mode is the tuition fee for learning. While a skill is maturing, the system pays more than it would without the skill -- it runs both the cheap local version and the expensive cloud version. This is an investment, not waste. The cloud LLM cost during shadow mode pays off as skills mature and shadow frequency drops to near zero. A skill that reaches STABLE has repaid its tuition many times over. The key metric is time to break-even: how many calls until the cumulative shadow cost is recovered by the per-call savings.

06 // HOW DOES THE SYSTEM KNOW WHAT'S EASY?

Not all patterns are equally forgeable. Some tasks are trivially reducible to deterministic code. Others are fundamentally semantic and will never descend below Tier 3 or 4. The system needs to estimate learnability before investing resources in a distillation attempt.

EvoSys computes a learnability score from several signals observed in the accumulated I/O pairs:

Signal Easy to Forge (Tier 0-1) Hard to Forge (Tier 4-5)
I/O mappingDeterministicVariable / creative
Output typeStructured JSONFree-form text
Schema consistency>95% across examples<80%
Examples needed5-10 sufficient50+ still ambiguous
Can describe in one sentenceYesNo

The learnability score is a weighted combination of these signals. High determinism, structured output, consistent schema, fast convergence with few examples, and a concise task description all push the score toward "easy." The system uses this score to prioritize which patterns to attempt forging first -- low-hanging fruit yields the fastest return on investment.

For ambiguous cases -- where the signals are mixed -- the system can escalate to the cloud LLM itself: "Given these 20 input-output examples, what implementation tier would you recommend?" This is meta-reasoning: using intelligence to decide how to deploy intelligence. It adds cost, but it's a one-time cost per skill class, not a per-call cost.

But ultimately, the safest strategy is empirical. Try the cheapest viable tier. Validate against ground truth. Escalate on failure. Theoretical learnability estimates are useful for prioritization, but the definitive answer comes from attempting the distillation and measuring the result.

07 // THE BOOTSTRAPPING PARADOX

There is a circularity at the heart of EvoSys that cannot be designed away: the system needs intelligence to decide how to deploy intelligence. Choosing the right tier for a skill requires understanding the task. Understanding the task requires the kind of reasoning that only the expensive tiers provide. The system must spend intelligence to save intelligence.

Early in its life, EvoSys will make bad decisions. It will try to forge tasks that are fundamentally unforgeable -- spending compute on a Tier 0 regex for a task that requires semantic understanding. It will pick the wrong tier, generate brittle code, and waste cloud LLM calls on shadow validation for skills that never converge.

This is expected. This is acceptable. Here is why:

First, each failure is bounded in cost. A failed forge attempt consumes a few LLM calls for code generation and a handful of test executions. The system sets budgets on distillation attempts -- if convergence isn't achieved within $N$ iterations or $M$ dollars, the attempt is abandoned and the skill stays at its current tier.

Second, each failure generates data that improves future decisions. A failed Tier 0 attempt for a semantic task teaches the system that tasks with similar learnability profiles should not be attempted at Tier 0. The failure history becomes a training signal.

Third, the heuristics that make early decisions get replaced by learned policies over time. The initial learnability scoring is hand-crafted -- a weighted sum of signals with manually chosen thresholds. But as the system accumulates a history of forge successes and failures, those outcomes become training data for a meta-learning model. The system literally learns how to learn.

"The alternative -- waiting until we have a perfect policy before starting -- means never starting."

Over time, the bootstrapping paradox resolves itself. The system's forge history -- which tasks succeeded at which tiers, which failed, what the learnability signals were -- becomes a dataset for predicting forge outcomes. The meta-learner gets better at picking tiers, which means fewer wasted attempts, which means faster skill maturation, which means more data for the meta-learner. A virtuous cycle, once you accept the cost of the cold start.

08 // WHEN MUSCLES ATROPHY

Skills degrade. This is not a bug -- it is an inevitable consequence of operating in a changing world. Websites restructure their HTML. APIs evolve their schemas. User expectations shift. A date parser that worked perfectly for US formats fails when the user base expands to Europe. A classifier trained on 2024 data drifts as language patterns evolve.

EvoSys monitors three staleness signals for every active skill:

1. Shadow divergence. Even after a skill reaches STABLE, the system periodically runs shadow comparisons at a low sampling rate (e.g., 1-5% of requests). When the skill's output begins diverging from what the cloud LLM produces on the same input, the divergence counter increments. A sustained divergence rate above threshold triggers a DEGRADED transition.

2. Error rate increase. Runtime errors -- exceptions, timeouts, malformed outputs, schema validation failures -- are tracked with an exponentially weighted moving average. A spike in error rate signals that something has changed in the input distribution or the external dependencies the skill relies on.

3. Input distribution shift. The system maintains a statistical fingerprint of each skill's input space -- simple features like string length distributions, character frequencies, or structural patterns. When new inputs deviate significantly from the training distribution, the skill is flagged for review even if it hasn't started failing yet. Prevention is cheaper than repair.

When a skill transitions to DEGRADED, the response is systematic: shadow mode goes back to 100%, fresh I/O pairs are collected from the cloud LLM, and the Forge re-attempts synthesis with the updated data. The old skill is not deleted -- it is archived with its full genealogy: the I/O pairs it was trained on, its test suite, its performance history, and the reason for its retirement.

Skills are never truly lost. A retired skill's test suite and accumulated I/O pairs are preserved as training data for its successor. The new version inherits its ancestor's knowledge, augmented with fresh examples that cover the drift. Evolution, not revolution.

09 // THE ROAD AHEAD

This post is Part 1 of the EvoSys design series, focused on the conceptual framework: what skills are, how they're tiered, how they mature, and how the system decides what to learn. The architecture has been described in terms of principles and processes. Now comes the engineering.

Phase 0 -- the data foundation -- is complete. This includes the data contracts and interfaces that define how skills communicate, the input/output sanitization layer, and the schema validation framework. The code is available in the EvoSys GitHub repository [1].

Phase 1 is trajectory logging: the all-seeing eye. Before the system can learn from its own operation, it needs to record that operation in structured, queryable form. Every LLM call, every tool invocation, every input-output pair must be captured with enough context to reconstruct the reasoning chain. This is the foundation on which pattern detection and skill synthesis will be built.

Phase 2 is the reflection daemon: the sleeping brain. A background process that analyzes trajectory logs offline, detects recurring patterns, estimates learnability, and proposes skill candidates to the Forge. This is where the system transitions from passive recording to active learning.

The hardest unsolved problems lie further ahead. Optimal DAG granularity: when a complex task decomposes into sub-tasks, how fine-grained should the decomposition be? Too coarse and the skills aren't reusable. Too fine and the coordination overhead dominates. Evaluation of semantic skills: how do you validate the output of a Tier 2 or 3 skill when the "correct" answer is fuzzy? Automated evaluation is itself a research frontier. The meta-learning feedback loop: training a model to predict forge outcomes requires forge outcomes, which requires attempting forges, which benefits from predicting outcomes. The chicken-and-egg problem at scale.

EvoSys is not a chatbot wrapper. It is not a prompt chain. It is not a RAG pipeline with a fancy name. It is an attempt to build a system that genuinely learns from its own operation -- one that gets better, faster, and cheaper with every task it completes. The muscles grow. The reflexes sharpen. The expensive intelligence is gradually freed to tackle problems that actually require it.
